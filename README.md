# vps-agent

MCP-сервер, который даёт кодинг-агенту (Claude Code или любому MCP-клиенту) управляемый доступ к VPS: команды, долгие задачи, интерактивные сессии, файлы, скриншоты, сервисы и nginx. Агент работает без root и действует только от имени пользователей, которых создал сам или которых ему передал администратор.

Наружу не открывается ни одного порта: клиент подключается обычным SSH и запускает `vps-agent serve` по stdio.

> Статус: v0–v2 написаны и проверены на Ubuntu 24.04. Опубликованных релизов пока нет, установка идёт из исходников. Что проверено, а что нет, перечислено в разделе [Статус проверки](#статус-проверки).

## Как это устроено

```
 ваша машина                         сервер
┌──────────────┐   SSH, stdio   ┌─────────────────────────────────────────┐
│ Claude Code  │───────────────▶│ agent (без пароля, без sudo)            │
│  └ vps-agent-mux (необяз.)    │  └ vps-agent serve   ← policy.toml (root)│
└──────────────┘                │       │                                 │
                                │       ├─ sudo -u <пользователь из списка>│
                                │       │    shop, blog, zos…             │
                                │       └─ sudo vps-agent-priv (root)     │
                                │            только типизированные действия│
                                └─────────────────────────────────────────┘
```

- **`vps-agent`** — MCP-сервер и CLI администратора. Работает от пользователя `agent`.
- **`vps-agent-priv`** — единственная точка, где агент получает root. Принимает фиксированный набор действий (создать пользователя, перезапустить разрешённый сервис, применить vhost), а не произвольные команды.
- **`vps-agent-mux`** — необязательный локальный мультиплексор: один MCP-сервер на несколько хостов.

### Чьими руками работает агент

| Пользователь | Откуда берётся | Что может агент |
| --- | --- | --- |
| `agent` | создаёт `install.sh` | входить по SSH, вызывать хелпер, переключаться в пользователей из списка |
| Управляемые | агент создаёт через `user_create` | всё от их имени; дом в `/srv/apps/<имя>`; может удалить |
| Усыновлённые | администратор: `vps-agent adopt <имя>` | всё от их имени, на месте, в их домашней папке; удалить не может |
| root и остальные | — | недоступны |

Управляемый пользователь определяется тремя признаками сразу: запись в реестре (`/var/lib/vps-agent-priv/users.json`, root), членство в группе `agent-managed`, UID из диапазона политики. Хелпер проверяет их при каждом переключении.

## Требования

- Сервер: Debian 12+ или Ubuntu 22.04+ с systemd, x86_64 или aarch64. Нужны `sudo` и `curl`; `tmux` — для сессий, `nginx` — для vhost'ов, Chromium — для скриншотов.
- Ваша машина: `ssh`, `bash` (на Windows — Git Bash), для сборки — Rust 1.95+.

## Установка из исходников

```bash
rustup target add x86_64-unknown-linux-musl aarch64-unknown-linux-musl
cargo build --release --target x86_64-unknown-linux-musl -p vps-agent -p vps-agent-priv
bash scripts/bundle.sh
bash scripts/connect.sh root@your-server --from target/x86_64-unknown-linux-musl/release
```

`connect.sh` запускается на вашей машине и рассчитан на то, что SSH-доступ к серверу у вас уже есть. Он:

1. создаёт ключ `~/.ssh/vps-agent_<host>` (приватный ключ не покидает машину);
2. копирует бинарники и `install.sh` на сервер и запускает установку;
3. добавляет `Host vps-agent-<host>` в `~/.ssh/config` и хост в `~/.config/vps-agent/hosts.toml`;
4. проверяет вход (`vps-agent selftest`) и регистрирует MCP-сервер в Claude Code.

Флаги: `--port <n>`, `--mode read-only|ask|auto`, `--name <alias>`, `--cert` (см. [Сертификаты](#короткоживущие-ssh-сертификаты)).

Кросс-сборка под musl идёт через `rust-lld` (настроено в `.cargo/config.toml`), отдельный тулчейн не нужен. Для ARM-сервера замените цель на `aarch64-unknown-linux-musl`.

Установка идемпотентна: повторный запуск обновляет бинарники и не трогает `policy.toml`.

## Инструменты

Все инструменты, кроме `user_*`, `sysinfo`, `nginx_*` и `system_service_*`, принимают `as_user` (по умолчанию `agent`).

| Группа | Инструменты |
| --- | --- |
| Команды | `exec` (ждёт завершения, по умолчанию 60 с) |
| Долгие задачи | `job_start`, `job_status`, `job_output`, `job_kill` |
| Сессии (tmux) | `session_open`, `session_send_keys`, `session_capture`, `session_close` |
| Файлы | `fs_read`, `fs_edit`, `fs_write`, `fs_upload`, `fs_download` |
| Картинки | `view_image`, `screenshot` (headless Chromium, только http/https URL) |
| Пользователи | `user_create`, `user_delete`, `user_list`, `user_linger` |
| Сервисы пользователя | `service_status`, `service_logs`, `service_control` (`systemctl --user`) |
| Системные сервисы | `system_service_status`, `system_service_logs`, `system_service_control` |
| nginx | `nginx_apply`, `nginx_remove` |
| Сервер | `sysinfo` |

Как вывод попадает к модели:

- `exec` отдаёт первые 50 и последние 150 строк, флаг `truncated` и `log_path`; полный вывод остаётся на сервере в `/var/lib/vps-agent/logs/`.
- Секреты, подходящие под шаблоны `[redact]`, заменяются на `[REDACTED]`. В логе на сервере остаётся оригинал.
- Весь вывод оборачивается в `<untrusted source="…">…</untrusted>`: это данные, а не инструкции для модели.

## Политика

Файл `/etc/vps-agent/policy.toml` принадлежит root; агент его прочитать может, изменить — нет. Проверяет политику сервер, а не клиент.

```toml
mode = "ask"            # read-only | ask | auto
uid_range = [20000, 29999]

[deny]
commands = ['rm\s+-rf\s+/(\s|$)', 'mkfs', 'dd\s+.*of=/dev/']
paths    = ["/etc/shadow", "/root", "/etc/vps-agent"]
groups   = []

[redact]
patterns = ['(?i)(password|secret|token|api[_-]?key)\s*[=:]\s*\S+', '-----BEGIN [A-Z ]*PRIVATE KEY-----']

[services]
allow = []
```

- **`read-only`** отключает все изменяющие инструменты; чтение работает.
- **`ask`** — режим по умолчанию: инструменты помечены аннотациями `destructive`/`readOnly`, подтверждение спрашивает клиент. Сервер жёстко держит только `read-only` и deny-списки, поэтому с клиентом, который игнорирует аннотации, `ask` ведёт себя как `auto`.
- **`deny.commands`** — регулярные выражения по тексту команды. Это страховка от очевидных ошибок, а не граница безопасности: граница — отсутствие root.
- **`deny.paths`** проверяются для файловых инструментов после нормализации пути и раскрытия симлинков.
- **`deny.groups`** дополняет встроенный список групп, в которые нельзя добавлять управляемых пользователей (`sudo`, `docker`, `adm` и другие).
- **`services.allow`** — системные сервисы, которыми агент может управлять, по точному имени юнита.

Каждый вызов инструмента пишется в journald с тегом `vps-agent`, каждый вызов хелпера — с тегом `vps-agent-priv`.

## Типовые сценарии

### Новое приложение в изоляции

1. `user_create` — пользователь `shop`, дом `/srv/apps/shop`.
2. Все дальнейшие вызовы с `as_user: "shop"`: клонирование, сборка, файлы.
3. `user_linger` (один раз), юнит в `~/.config/systemd/user/`, затем `service_control`: `daemon-reload`, `enable`, `start`.
4. `nginx_apply` публикует приложение, слушающее `127.0.0.1`.

### Существующее приложение под существующим пользователем

Папку переносить не нужно. Администратор один раз:

```bash
sudo vps-agent adopt zos
```

и, если приложение работает как системный сервис, добавляет его в политику:

```toml
[services]
allow = ["zoschedule-bot.service"]
```

После этого агент выполняет `git pull` и сборку от имени `zos` прямо в его домашней папке и перезапускает сервис через `system_service_control`. Установку или изменение самого unit-файла агент сделать не может: запись в `/etc/systemd/system` равна root-доступу.

Учтите: если усыновлённый пользователь состоит в группе `sudo`, агент не получает root (пароля у него нет), но может менять файлы этого пользователя, включая `.bashrc`. Для пользователей приложений `sudo` лучше убрать.

### nginx

`nginx_apply` принимает имя и содержимое vhost'а, кладёт его в `/etc/nginx/sites-agent/<имя>.conf`, запускает `nginx -t` и делает reload. При ошибке файл откатывается, работающий nginx не затрагивается.

Мастер-процесс nginx работает от root, поэтому часть директив отклоняется: логи разрешены только в `/var/log/nginx/`, TLS-файлы — только в `/etc/letsencrypt/` и `/etc/ssl/`; `include`, `load_module`, встроенные скрипты и `*_temp_path`/`*_cache_path` запрещены. Это список запретов по именам директив, а не полный разбор конфигурации.

## Команды администратора

Выполняются на сервере от root, агенту недоступны.

| Команда | Что делает |
| --- | --- |
| `vps-agent adopt <user>` | передаёт существующего пользователя агенту (UID 0 — никогда) |
| `vps-agent off` | аварийный выключатель: снимает sudoers-правило, отключает SSH-ключ и вход по сертификату, останавливает HTTP-эндпоинт, убивает процессы агента и его пользователей |
| `vps-agent on` | возвращает доступ (HTTP-эндпоинт остаётся остановленным) |
| `vps-agent http-setup` | настраивает remote MCP, печатает секрет сопряжения |
| `vps-agent selftest` | проверка установки; запускается от `agent` |

## Несколько хостов: vps-agent-mux

```bash
cargo build --release -p vps-agent-mux
claude mcp add vps-agent -- vps-agent-mux
```

Мультиплексор читает `~/.config/vps-agent/hosts.toml` (или путь из `VPS_AGENT_HOSTS`):

```toml
[hosts.prod]
ssh = "vps-agent-prod"            # алиас из ~/.ssh/config или user@host

[hosts.stage]
ssh = "ssh://agent@10.0.0.5:2222"
identity = '~/.ssh/vps-agent_stage'
ca_key = '~/.ssh/vps-agent_ca'    # включает режим сертификатов
cert_minutes = 5
```

У каждого инструмента появляется параметр `host`; инструмент `hosts` показывает список и доступность. После обрыва связи следующий вызов переподключается сам. Если связь оборвалась посреди вызова, мультиплексор его не повторяет, а возвращает ошибку «команда могла выполниться»: повтор мог бы запустить её дважды.

`vps-agent-mux check` проверяет подключение ко всем хостам.

## Короткоживущие SSH-сертификаты

```bash
bash scripts/connect.sh root@your-server --from <dir> --cert
```

Вместо постоянного ключа в `authorized_keys` сервер доверяет локальному CA (`~/.ssh/vps-agent_ca`), причём только для пользователя `agent`. Мультиплексор перед каждым подключением подписывает сертификат на несколько минут. Украденный с вашей машины ключ агента без CA бесполезен, а выданный сертификат быстро истекает.

На сервере это файл `/etc/ssh/sshd_config.d/50-vps-agent.conf`; `install.sh` проверяет конфигурацию через `sshd -t` перед перезагрузкой sshd и откатывает файл при ошибке. Ключ CA создаётся без пароля — храните его как секрет.

## Remote MCP по HTTP (для claude.ai)

```bash
sudo vps-agent http-setup --public-url https://mcp.example.com
```

Команда пишет `/etc/vps-agent/http.toml` и юнит `vps-agent-http.service`, один раз печатает **секрет сопряжения** и пример vhost'а. Дальше:

1. Поставьте TLS-прокси перед `127.0.0.1:8722` (эндпоинт слушает только loopback и отказывается от публичного bind).
2. `systemctl enable --now vps-agent-http`.
3. Добавьте `https://mcp.example.com/mcp` как custom connector.

Авторизация — встроенный OAuth 2.1: динамическая регистрация клиентов, authorization code с PKCE (только S256), ротация refresh-токенов. Учётных записей нет: на странице согласия владелец сервера вводит секрет сопряжения. Пять неверных попыток блокируют подтверждение на 5 минут. Токены хранятся на диске только в виде хешей.

Этот режим открывает shell-доступ через интернет за одним секретом. Включайте его осознанно и держите `mode = "ask"` или `read-only`.

## Плагин Claude Code

Каталог `plugin/` содержит MCP-конфиг (запускает `vps-agent-mux`), скилл с правилами работы на сервере и PreToolUse-хук. Хук переспрашивает подтверждение перед труднообратимыми вызовами (`rm -rf`, запись на диск, `curl | sh`, `DROP TABLE`, удаление пользователя), даже если в сессии включено автоодобрение. Он ничего не блокирует: ограничения держит политика на сервере.

## Удаление

```bash
sudo bash dist/uninstall.sh --users keep|archive|purge
```

Управляемых пользователей можно оставить, удалить с архивом домашних папок или удалить полностью. Усыновлённые пользователи только выводятся из группы `agent-managed`.

## Разработка

```
crates/vps-agent-core   чистая логика: имена, политика, обрезка вывода, реестр, фильтр nginx
crates/vps-agent-priv   root-хелпер: типизированные действия поверх трейта System
crates/vps-agent        MCP-сервер, инструменты, HTTP/OAuth, CLI администратора
crates/vps-agent-mux    локальный мультиплексор
scripts/                install.sh, uninstall.sh, connect.sh, bundle.sh, lib/ui.sh
plugin/                 плагин Claude Code
tests/                  приёмочные сценарии для настоящего сервера
```

```bash
cargo test --workspace
shellcheck -x scripts/*.sh scripts/lib/ui.sh plugin/hooks/guard.sh tests/*.sh
```

Юнит-тесты покрывают чистую логику и запускаются на любой ОС. Всё, что требует Linux, проверяется приёмочными сценариями на сервере:

| Сценарий | Где запускать | Что проверяет |
| --- | --- | --- |
| `tests/acceptance.sh` | на сервере от root | права, sudoers, хелпер, реестр, аварийный выключатель |
| `node tests/mcp-accept.mjs <ssh-алиас>` | на своей машине | все MCP-инструменты через stdio; `ACCEPT_NGINX=1` добавляет живой тест nginx |
| `node tests/mux-accept.mjs <exe> <hosts.toml> <host>` | на своей машине | мультиплексор и переподключение |
| `tests/http-accept.sh` | на сервере от root | HTTP-эндпоинт и OAuth на loopback, убирает за собой |
| `node tests/call.mjs <ssh-алиас> <tool> '<json>'` | на своей машине | разовый вызов инструмента |

`scripts/bundle.sh` склеивает `lib/ui.sh` в `dist/install.sh` и `dist/uninstall.sh`, чтобы они работали через `curl | bash`.

## Статус проверки

Проверено на Ubuntu 24.04 (x86_64): установка через `connect.sh`, все инструменты v0 и v1, включая живой `nginx_apply` с откатом; системные сервисы; усыновление пользователя и обновление реального приложения на месте; мультиплексор с обрывом связи; вход по сертификатам с отказами и аварийным выключателем; OAuth-поток на loopback.

Не проверено:

- `screenshot` с настоящим Chromium;
- remote MCP с настоящим claude.ai (нужны домен и TLS);
- плагин в живой сессии Claude Code (манифест проходит `claude plugin validate`);
- `uninstall.sh`;
- релизный workflow GitHub Actions и установка из релиза (`curl | bash`), проверка подписи minisign;
- aarch64 (собирается, не запускался) и Debian.
